# 集成实现（家庭数据抽象）

> 本文属于 [API 工作原理](../API工作原理.md) 的「集成实现」部分。

集成 `custom_components/netease_intelligent/` 在登录（见 [登录流程](./登录流程.md) 的「集成实现」）之上，用「模型 + 客户端 + 协调器」三层抽象家庭数据，作为设备/场景实体的地基：

| 文件 | 职责 |
|------|------|
| `models.py` | 家庭域 DTO（`FamilyInfo`/`Family`/`Room`/`Member`/`FamilyEquip`/`Equip`/`FamilyEnv`/`EnvInfo`）与扫地机数据 DTO（`SweeperDeviceData`）。字段为 `snake_case`，`from_dict` 按 `camelCase` 映射回 API JSON 键（如 `family_id` ← `familyId`），缺字段容错。 |
| `api.py` | `NeteaseIntelligentApiClient`：按 [认证机制](./认证机制.md) 注入 `Cookie`（`ONE_TOKEN` / `ONE_TOKEN_ID` / `UA-INFO`），按 [统一响应结构](./统一响应结构.md) 解包 `ResponseWrapper`（`code != 0` 抛 `ApiError`），返回模型对象。 |
| `coordinator.py` | `NeteaseIntelligentCoordinator`（`DataUpdateCoordinator`）：周期拉取 `GET /ai-app/family/info`，按家庭 ID 建索引存入 `coordinator.data`。`NeteaseIntelligentSweeperCoordinator` 缓存单台扫地机实时数据：以 `getDeviceData` 轮询为**基础**、官方推送**实时增补**（见下文「状态更新：轮询为基础 + 推送实时增强」）。 |
| `push.py` / `push_protocol.py` | 官方 Socket.IO 推送通道客户端与其纯逻辑层（帧解析、载荷→`SweeperDeviceData` 映射、`pushId` 生成）；`iot_class` 为 `cloud_push`，推送掉线时轮询继续提供数据。 |
| `__init__.py` | 建客户端与协调器，`async_config_entry_first_refresh` 首次校验凭据，存入 `hass.data[DOMAIN][entry_id]`；并把家庭数据中的扫地机器人登记进 HA 设备注册表，为每台（有 `equipId` 的）扫地机建 `SweeperCoordinator`，装配 `vacuum`/`sensor` 实体。 |
| `vacuum.py` / `sensor.py` | 扫地机器人实体：`vacuum`（`StateVacuumEntity` + `VacuumActivity`，清扫/暂停/回充/吸力/寻找设备）与 `sensor`（电量、今日清扫面积、今日清扫时长）。控制指令后对 `vacuum` 采用乐观更新（见下文「状态更新：轮询为基础 + 推送实时增强」）。 |

已实现端点：`GET /ai-app/family/info`（家庭列表）、`GET /ai-app/family/query`（单家庭）、`GET /ai-app/family/env/info/homepage`（家庭环境信息）、`GET /ai-app/equip/list`（设备列表）、`GET /ai-app/sweeper/rv02/getDeviceData`（扫地机实时数据）、`POST /ai-app/sweeper/rv02/setWorkMode`（清扫模式/动作控制）、`POST /ai-app/sweeper/rv02/setPreference`（偏好：吸力等）、`POST /ai-app/sweeper/rv02/deviceCtrl`（设备控制：寻找等）；另为推送通道使用 `GET /ai-app/account/info`（账号信息，取 `pid` 拼 `uid`）与 `GET /ai-app/app/event/view`（开始/关闭推送）。

## 扫地机器人设备识别与登记

扫地机器人由 `Equip.productId` 区分：`RV02 = 9`、`RV03 = 26`（Pro 款，见 `sweeper/config/SweeperConfig.java` 与 `kernel/presenter/entry/Product.java`；集成侧以 `const.SWEEPER_PRODUCT_IDS = {9, 26}` 表示）。

- 设备标识：`Equip.sn`（序列号）优先，缺失时回退到 `Equip.id`（即 `equipId`，也是调用 sweeper 端点的入参，见 `GET /ai-app/sweeper/rv02/getDeviceData?equipId=<id>`）。
- 登记位置：`__init__.py` 首次刷新后遍历 `coordinator.data` 各家庭的 `Family.equips`，过滤出扫地机并写入 `device_registry.async_get_or_create(...)`；同时 `coordinator.async_add_listener` 在每次刷新后重跑，覆盖设备的新增/移除。
- 实体：每台有 `equipId`（`Equip.id`）的扫地机建一个 `NeteaseIntelligentSweeperCoordinator`，其数据以 `GET /ai-app/sweeper/rv02/getDeviceData?equipId=<id>` 轮询为**基础**（提供完整字段与首次全量基线），并由官方推送通道**实时增补**，据此装配：
  - `vacuum` 实体（`StateVacuumEntity` + `VacuumActivity`）：由 `workMode` + `chargeStatus` + `faultCode` + `faultType` 映射清扫状态（清扫/暂停/回充/充电中(docked)/空闲/错误，映射纯函数 `const.sweeper_activity`）。错误仅由 `faultType == 1` 判定（App 的 `ErrorToast` 亦仅据此显示错误横幅）；`faultCode` 非 0 **不代表错误**——2101/2103/2105 为「在充电座/充电中」等状态，与 `chargeStatus` 一起用于判定「在充电座」（`docked`，即 App 的 `SweeperManager.isRobotInCharger()`）：回充中（Recharge 与各 `*Complete_Recharge`，App 文案均为「回充中」）与断点（含 `Auto_Breakpoint`，码值 `11`）在未到座时映射为 `returning`。吸力 `windPower` 映射为 fan_speed（关闭/安静/标准/强劲）；支持启动/暂停/停止/回充（`setWorkMode`）、吸力（`setPreference`）、寻找设备（`deviceCtrl`）。
  - `sensor` 实体：电量（`battery`，%）、今日清扫面积（`todayCleanSize`，接口返回面积×100、除以 100 得㎡）、今日清扫时长（`todayCleanTime`，分钟）。
- 电量不放 `vacuum` 的 `battery_level`（HA 2025.8 起废弃），改用独立 `sensor`；仅登记设备、无 `equipId` 的扫地机不建实体。

## 状态更新：轮询为基础 + 推送实时增强

`manifest.json` 的 `iot_class` 为 `cloud_push`：集成启动时建立官方 Socket.IO 长连接（`push.py`），实时接收设备状态/地图推送并注入各 `NeteaseIntelligentSweeperCoordinator`。但推送只是**增量补丁**，轮询才是**基础数据源**——它提供推送不覆盖的字段（如 `todayCleanSize`/`todayCleanTime`）与首次全量基线，并且始终可用；因此推送不可用（未取到 `pid`、连接失败、断开）时无需“切换”，轮询本就一直在按固定间隔运行。

- **推送（实时增强）**：`push.py` 的 `NeteaseIntelligentPushClient` 连接 `wss://3c.163.com/socket.io/`，注册 `pushId`、`bindUid(r_intelligent_<pid>)` 后对每台扫地机调用 `GET /ai-app/app/event/view`（`eventType=1` 开始推送）；收到 `42["p", ...]` 帧由 `push_protocol.decode_push_frame` 解析、`merge_sweeper_patch` 合并进协调器缓存（`coordinator.apply_sweeper_push`），实体立即刷新。断开时指数退避重连，卸载集成时发 `eventType=2` 关闭推送。
- **轮询（基础数据源）**：频率**固定，不随设备状态或控制指令变化**——推送在线时降频到 `SWEEPER_UPDATE_INTERVAL_PUSH_ONLINE`（10min），推送不可用时用 `UPDATE_INTERVAL`（5min）。轮询负责推送不覆盖的字段（`todayCleanSize`/`todayCleanTime` 等）与首次全量基线；**从不提速**（状态时效由推送承担，给轮询提速会打爆设备/云）。家庭数据协调器同用 `UPDATE_INTERVAL` 5min。
- **控制后即时反馈**：`vacuum` 实体的控制指令（开始/暂停/停止/回充/吸力）发出后先做**乐观更新**（立即把 `activity`/`fan_speed` 改为预期值并写回状态），并立即刷新一次（单次请求，不改动轮询频率）；乐观值在设备数据变为与命令前不同（视为设备已回报，通常由推送触发）或超过 `ASSUMED_STATE_TTL`（60s）后清除。

### 可能取不到 `pid` 的情况

`pid` 由 `GET /ai-app/account/info?from=1` 返回（`UserInfo.pid`，`long`，缺省 `0`），是 `bindUid` 与推送订阅的前提。App 侧 `Auth.java` 同样以 `pid == 0` 判定「未登录 / 无有效用户」。实际只有两类会取不到 `pid`，且均为异常；任一情况仅**不启用推送**（`__init__._async_setup_push` 记 warning），数据由轮询提供：

- **未登录 / 凭据失效**：`from=1` 需已登录，未登录或 `ONE_TOKEN` 过期时 `UserInfo.pid` 为 `0`。（`Auth.java:84`/`:386` 即以 `pid == 0` 作为未登录判据；凭据失效通常还会使首次刷新失败、整个集成不可用，而不只是推送。）
- **账号信息请求失败**：网络超时 / DNS 失败 / 非 200 / `code != 0`（被风控）→ 抛 `ApiError`。

> `UA-INFO` 不是变量：登录与手动录入流程都不写入该 Cookie，`api.py` 在缺失时用 `build_ua_info()` 自动生成，请求头始终完整，因此与 `pid` 获取无关。

### 为什么轮询不可省（即使推送可用）

在**存在扫地机**（确有实体需要更新）的前提下，仅靠推送无法完整支撑状态，轮询是基础而非可选项：

- **推送字段是 `getDeviceData` 的子集**：subtype 1 只含 `area_clean_flag`/`battery`/`charge_status`/`clean_scheme_id`/`clean_size`/`clean_time`/`fault_code`/`fault_type`/`map_id`/`protocol_version`/`repeat_clean`/`water_control`/`wind_power`/`work_mode`（见 `push_protocol._STATUS_FIELDS`）。**不含 `todayCleanSize`、`todayCleanTime`、`isOnline`、`isOtaUpdating`、`isRoomCleaningStatus`** —— 其中 `todayCleanSize`/`todayCleanTime` 正是 `sensor`「今日清扫面积 / 时长」的唯一数据源，`isOnline`（离线判断）同理；这些字段**只能**通过 `GET /ai-app/sweeper/rv02/getDeviceData` 获得。
- **需要全量基线**：推送是补丁，`coordinator.apply_sweeper_push` 在缓存为空（`data is None`）时直接忽略；必须由 `async_config_entry_first_refresh`（及后续轮询）先建立全量基线，推送才有意义。
- **通道可靠性**：推送依赖网易内部协议（无 SLA），可能被风控 / 限流 / 静默丢帧或因协议变更失效；重连退避期间还存在数据空窗。
- **取不到 `pid` 时没有其它通道**：上述「取不到 `pid`」的所有情形下，轮询是唯一可用来源。

## 官方推送通道

官方 App **不用轮询**，而是走 Socket.IO 长连接推送（`com.yy.httpproxy` 框架）。本集成已按下列协议实现（`push.py` + `push_protocol.py`）；协议要点经实抓 HAR 与在线探针 `scripts/push_probe.py` 验证：

- **连接**：`wss://3c.163.com/socket.io/?EIO=3&transport=websocket`，**无 Cookie/Header**；客户端每 ~20s 发 Engine.IO ping `2`，服务端回 `3`（不发心跳约 60s 被断开）。
- **注册**：`emit pushId {id, platform:"android", topics:["noti","event"], lastPacketIds}` → 服务端回显确认；随后 `emit setTags` / `unbindUid` / `bindUid {uid:"r_intelligent_<pid>"}`。
- **uid 构造**：`ENV="r"`（release，`AlcsConstant.MODE_VALUE_READ`）+ `APP_NAME="intelligent"`（`R.string.host_push_product_name`）+ 账号 `pid`（`GET /ai-app/account/info?from=1` → `UserInfo.pid`）。
- **开始/关闭推送**：进入设备页调用带鉴权的 `GET /ai-app/app/event/view?pushId=&productId=&eventType=&equipId=`（`eventType=1` 开始推送、`2` 关闭推送，返回 `{"code":0}`）；需 `ONE_TOKEN`/`ONE_TOKEN_ID`/`UA-INFO` Cookie（来源 `kernel.util.EventUtil` + `sweeper.modules.home.HomeActivity`）。
- **推送帧**：事件名 `"p"`，正文在 `android.payload.data.json = {eventType:1, subtype, type:productId, payload}`。
- **subtype**：`1`=设备状态（字段为 `getDeviceData` 的**子集**，缺 `todayCleanSize`/`todayCleanTime`/`isOnline`/`isOtaUpdating` 等，可直接映射 `SweeperDeviceData`；这些缺口字段仍需轮询补齐，见上文「为什么轮询不可省（即使推送可用）」）、`2`=地图（`mapUrl`）、`3`=轨迹（`position` 数组）、`4`=待确认地图。subtype 2 的帧按官方 `flowMapPush` 过滤：`mapType` 为 Zone(2)/Spot(3)/Memory(5) 或 `mapUrl` 为空时忽略，仅 Normal(1)/History(4) 更新实时地图。**注意 `mapUrl` 往往是固定 URL，服务端在其上覆盖写入新内容**（实测同一 URL 的包内 `robot.poseId` 随时间增长），因此 `image` 实体不能只按 URL 相等判定缓存，而要在每次 subtype 2 推送（`coordinator.map_revision` 自增）时重新下载。
- **实时轨迹（subtype 3）**：官方 App 清扫中地图的「增长」完全来自 subtype 3——`HomeActivity.updateHistory` 取 `SweeperPushHistory.position`（`int[]`）交给 `MapController.setHistory`，`MapHistoryParser` 仅对 `update==1` 的点以 7×7 画笔把「未到达」标为「已到达」（房间态同理）并在相邻点间插值补点，随后重渲染。`image` 实体已复刻该流程（`map_parser.parse_trajectory` / `apply_trajectory` / `trim_baked_history`）：累计已应用的轨迹点，`map_history` 变化时增量重放；同 URL 刷新地图包时按 `robot.poseId` 裁掉服务端已烘焙的点再重放（避免已清扫着色被抹掉），仅当 `mapUrl` 变化才视为新地图并清空累计。**记录布局**：实抓推送为**每记录 6 个 int** `[mapHeadId, poseId, update, poseX, poseY, posePhi]`（坐标为米 ×10000，`posePhi` 为弧度 ×10000，如 `±31414≈±π`），与官方消费端 `MapHistoryParser.translate` 一致；`push_protocol` 侧日志会打印 `position` 长度与片段以便核对。集成的宽度检测按「6 优先、3 回退」以兼容旧文档描述的三值 `[poseX, poseY, update]`。
- **多端共存**：同一 `uid` 允许多个 pushId 同时订阅，实测与官方 App 并存不互踢。
- **验证工具**：`scripts/push_probe.py <pid> [--watch N] [--ping N] [--har HAR] [--equip-id ID] [--product-id N]`；不给 `--equip-id` 时仅被动监听，给出后额外复刻官方「开始/关闭推送」（`event/view`，需 `--har`/`--cookie` 提供鉴权）。
- **风险与容错**：推送依赖网易内部协议（无 SLA、可能变更/风控），因此仅作实时增量增强，轮询始终保留；未取到 `pid` 或连接失败/断开时无需切换，轮询本就按自适应间隔持续运行。

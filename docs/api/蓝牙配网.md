# 蓝牙配网（BLE 下发 Wi-Fi 凭据）

> 本文属于 [API 工作原理](../API工作原理.md) 的「蓝牙配网」部分。
>
> 说明网易智造 App（`com.netease.intelligent` 5.3.5）扫地机通过 **BLE GATT** 把家庭 Wi-Fi 凭据下发给设备、读回设备 SN，再到云端完成绑定的完整链路。涉及端点见 [`openapi.yaml`](../openapi.yaml)：`/ai-app/product/list`、`/ai-app/equip/status`、`/ai-app/equip/bind`。

## 结论先行

- 蓝牙只承担 **「把 Wi-Fi 账号密码送进设备 + 取回设备 SN」** 这一小段；设备联网、上线、绑定全部走云端 HTTP。
- 报文是**自定义分片帧**（16 字节一片），写在产品配置指定的 write 特征上，每片间隔 200 ms；2 秒后从 read 特征读回 JSON，`deviceName` 即 SN。
- 目标服务/特征 UUID **不写死在代码里**，来自产品配置 `bleConfig`（服务端下发、AES 加密），因此不同型号可能完全不同。
- 扫地机走这条链路时 `is3irobotics=true`：读回 SN 后必须轮询 `/ai-app/equip/status` 直到设备 `ON_LINE`，才调用 `/ai-app/equip/bind`。
- 配网全程**不连设备热点**；连接失败时可回退到热点配网（`fromBle=false`），那是另一条 SoftAP/UDP/TCP 链路。

## 入口与触发条件

入口在扫地机模块：`sweeper/api/SweeperEntry.showBind()`。

```
ProductPresenter.getProductById(productId)
  ├─ bleConfig != null && wifiConfig != null → BindEntry.bindBluetoothEquip(...)   // 本流程
  ├─ wifiConfig != null                      → BindEntry.configAndBindWifiEquip(...) // 热点配网
  └─ 都为 null                               → 不做任何事
```

`bindBluetoothEquip` 的实参（`SweeperEntry` 硬编码部分）：

| 参数 | 取值 | 来源 |
|------|------|------|
| `bluetoothNamePattern` | `bleConfig.namePattern` | 产品配置 |
| `guideWebUrl` | `wifiConfig.wifiGuidePage` | 产品配置 |
| `guideConfirmText` | `bleConfig.confirmText` | 产品配置 |
| `usingNameAsSN` | `bleConfig.usingNameAsDN` | 产品配置 |
| `showSN` | `bleConfig.showDN` | 产品配置 |
| `showHelp` | `true` | 硬编码 |
| `is3irobotics` | `true` | 硬编码 |

进入 `BluetoothBindActivity`（布局 `kernel_activity_bluetooth_bind`，标题「绑定设备」）。

## 产品配置如何下发（关键前置）

`GET /ai-app/product/list` 返回的 `Product` 里，`bleConfig` / `wifiConfig` 都是**加密字符串**，由 `Product.decryptedBleConfig()` / `decryptedWifiConfig()` 解密（`util/ciphers/Aes`）：

| 项 | 值 |
|----|----|
| 算法 | `AES/CBC/PKCS5Padding` |
| key | `6DABB8E9D09D00C987F8EE42D251A53E`（32 个 ASCII 字符直接当密钥字节） |
| iv | `20342B9E8868D1A8`（16 个 ASCII 字符） |
| 编码 | 输入先 Base64 解码，输出 UTF-8 JSON |

解密后的 `BleConfig`：

```jsonc
{
  "namePattern": "…",        // 蓝牙名正则（Java Pattern，find 匹配）
  "guideWebUrl": "…",
  "confirmText": "…",
  "usingNameAsDN": false,    // true 时用蓝牙名当 SN
  "showDN": false,           // 是否在扫描列表展示 SN
  "serviceInfo": {
    "Android": {
      "read":  "<serviceUUID>#<characteristicUUID>",
      "write": "<serviceUUID>#<characteristicUUID>"
    }
  }
}
```

`read` / `write` 用 `#` 拼接服务与特征 UUID（完整 128 位字符串），代码按字符串相等匹配。

## 全流程时序

```
App                         扫地机(BLE)                  云端
 │  startLeScan(10s)            │                          │
 │──按 namePattern 过滤────────▶│                          │
 │  connectGatt                 │                          │
 │──discoverServices───────────▶│                          │
 │  write 帧 0..N（间隔 200ms）  │                          │
 │──{"ssid","pwd","addr"}──────▶│                          │
 │                              │  连 Wi-Fi                │
 │  delay 2s                    │                          │
 │  read 特征                   │                          │
 │◀──{…,"deviceName":"SN"}──────│                          │
 │                              │                          │
 │  GET /ai-app/equip/status?productId=&sn=  ─────────────▶│
 │◀────────────────────────────── status=ON_LINE ──────────│
 │  POST /ai-app/equip/bind     ──────────────────────────▶│
 │◀────────────────────────────── 绑定成功（Equip）────────│
```

对应代码：`kernel/bind/ui/BluetoothBindActivity`（扫描/连接）→ `kernel/bind/ui/WifiBindActivity.configAndBindDefault()` 的 `mIsFromBle` 分支（下发/读回/校验/绑定）。

## 扫描与设备识别

`BluetoothBindActivity.scan()`：

- 页面先展示引导页（`BluetoothBindGuideFragment`：配图/动画 + `wifiGuidePage` + 「下一步」按钮），点「下一步」才真正开始扫描。
- 底层 `BluetoothLowEnergyConnection.scan()` 用 `BluetoothAdapter.startLeScan()`（**不是** `BluetoothLeScanner`，无 `ScanFilter`），超时 **10 秒**；本流程 `serviceUuid = null`，即扫描全部广播。
- 过滤在应用层：`Pattern.compile(bleConfig.namePattern).matcher(device.getName()).find()`，蓝牙名为 `null` 直接丢弃。
- 按 MAC 去重；列表项显示产品名 + `SN`（`showSN=true` 时可见）。SN 取值规则见下节。
- 10 秒内一台都没扫到 → 切到「未找到」页（`BluetoothBindNotFoundFragment`），文案：

  > 无法搜索到设备的常见原因：
  > 1、设备已与其他手机蓝牙建立连接
  > 2、设备未进入配网模式

- 扫描前会检查定位权限与蓝牙开关，未满足则拉起 `base/bluetooth/util/OpenBluetoothActivity`；回调 `0` 表示成功、`-1` 表示失败（`BluetoothEntry.openBluetooth`）。

### 设备身份（SN）与蓝牙 MAC

`BluetoothBindActivity.buildBindDevice()`：

```kotlin
bluetoothMacAddr = EquipUtil.translateBluetoothAddress(device.address) // "AA:BB:CC:DD:EE:FF" → "AABBCCDDEEFF"（去冒号、转大写）
sn = if (usingNameAsSN) device.name else bluetoothMacAddr
```

`usingNameAsSN = bleConfig.usingNameAsDN`。注意 `BluetoothBindActivity.Companion.buildIntent()` 把 `guideConfirmText` 与 `usingNameAsSN` 写进了**同一个 key** `"guideConfirmText"`（先 `String` 后 `Boolean`，后者覆盖），而 `mUsingNameAsSN` 读的正是该 key 的 `Boolean`；副作用是 `bleConfig.confirmText` 实际不会显示（`getStringExtra` 取到 `Boolean` 时返回 `null`）。

### 点击设备后

- `wifiConfig.ssidPattern != null`（正常扫地机）：停止扫描 → `BleHelper.connect(device)` → 成功后携 `fromBle=true` 跳 `WifiBindActivity`（`skipGuide=true`，直接进 Wi-Fi 选择页）。
- `wifiConfig` 缺失：**纯蓝牙绑定**——不配网，直接用上一步的 `Equip`（`bluetoothMacAddr` + `sn`）调 `/ai-app/equip/bind`。

连接失败弹窗（`kernel_bind_ble_connect_fail`）：

> 设备蓝牙连接失败
>
> 可能由于设备已被其他手机蓝牙连接，或未处于配网模式中。
> 排除以上原因后，可「立即重试」，或尝试切换为 Wi-Fi 热点配网方式

按钮：**立即重试**（重连）、**尝试热点配网**（同参数重开 `WifiBindActivity`，`fromBle=false`）、**稍后再试**（退出）。

## BLE 连接与 GATT 参数

| 项 | 实现 |
|----|------|
| 连接 | `device.connectGatt(context, false, gattCallback)`，超时 10 s（`BluetoothLowEnergyConnection.connect`） |
| 服务发现 | `discoverServices()`，超时 10 s；已缓存服务时直接回调，不重复发现 |
| write 特征 | `bleConfig.serviceInfo.android.write`，`setValue()` + `writeCharacteristic()`，**默认 `WRITE_TYPE_DEFAULT`（有响应）** |
| read 特征 | `bleConfig.serviceInfo.android.read`，`readCharacteristic()`，结果在 `onCharacteristicRead` 回调 |
| notify | 该链路**不使用**通知（`notify()` 虽实现了 CCCD 写入，但未被调用） |
| 线程 | 所有 GATT 回调统一切主线程 |
| 关闭 | 读完后 `stopConnect()`；Activity 销毁时 `close()` |

## 报文格式

### 下行（App → 设备）

`BleHelper.buildWifiDeque()` 把 JSON 的 UTF-8 字节按 **16 字节**切片，`total = ceil(len / 16)`，逐帧：

| 偏移 | 长度 | 含义 |
|------|------|------|
| 0 | 1 | `seq`，从 0 开始 |
| 1 | 1 | `len`，本片实际字节数（1..16） |
| 2 | 1 | `total`，总片数 |
| 3 | `len` | 载荷（JSON 片段） |
| 3+len | 1 | 校验字节 |

校验字节是四个字节的**按位与**（不是 XOR）：

```kotlin
checksum = (seq and len and total and payload[0]).toByte()
```

（已用 `dexdump` 核对 `buildWifiDeque` 的字节码为 `and-int`。）由于按位与极易为 0（例如 `len=16` 时 `0x10 and 0x04 = 0`），实际发出的校验几乎恒为 `0x00`，设备侧也不校验。

每帧写入后 `Thread.sleep(200)`，即约 **5 帧/秒**。

示例：`{"ssid":"A","pwd":"12345678","addr":"3c.163.com"}`（49 字节，`total=4`）

```
帧0: 00 10 04 | 7B 22 73 73 69 64 22 3A 22 41 22 2C 22 70 77 64 | 00
帧1: 01 10 04 | 22 3A 22 31 32 33 34 35 36 37 38 22 2C 22 61 64 | 00
帧2: 02 10 04 | 64 72 22 3A 22 33 63 2E 31 36 33 2E 63 6F 6D 22 | 00
帧3: 03 01 04 | 7D | 00
```

（末字节为校验，按上式算得均为 `00`。）

### 上行（设备 → App）

`BleHelper.read()` 读到的帧：

| 偏移 | 长度 | 含义 |
|------|------|------|
| 0 | 1 | `seq`，从 0 开始 |
| 1 | 1 | `len`，本片载荷字节数 |
| 2 | 1 | `total`，总片数 |
| 3 | 1 | 命令字，**必须为 `0x03`** |
| 4 | `len` | 载荷 |

校验规则（任一不满足即报错）：

| 条件 | 异常 |
|------|------|
| `data.length < 5` | `Exception("Read: Data length error")` |
| `data[3] != 3` | `Exception("Read: Command error")` |
| `data[0] < data[2] - 1`（还有后续片） | `ReadNext("未读取完毕")`，100 ms 后重读 |

累计所有片后 `stopConnect()`，把字节拼成 UTF-8 JSON。

## 下发的数据

`WifiBindActivity.configAndBindDefault()`（`mIsFromBle` 分支）：

```jsonc
{
  "ssid": "<mWifiSsid>",
  "pwd":  "<mWifiPassword>",
  "addr": "3c.163.com"   // API.HELPER.get() 去掉 "https://"
}
```

- `addr` 就是 **Base URL 去掉 scheme**（线上 `3c.163.com`，测试环境相应变化），设备据此找云端。复刻时必须与目标环境一致。
- SSID/密码来自用户在 `WifiBindConfigureFragment` 的选择（`setWifiConfig(ssid, bssid, pwd, frequency, capabilities, remember)`）。
- 该页面仍需 **定位权限**（`ACCESS_COARSE_LOCATION` + `ACCESS_FINE_LOCATION`）与系统定位开关，因为要扫描 Wi-Fi 列表——即使走 BLE。

响应 JSON 取 `deviceName` 作为设备 SN：

```jsonc
{ "deviceName": "<SN>", … }
```

## 上线校验与云端绑定

`is3irobotics=true`（扫地机）时，读回 SN 后先校验设备是否已上线：

```
delay 5s → GET /ai-app/equip/status?productId=<id>&sn=<SN>
  status == ON_LINE → 继续
  否则抛 EquipNotOnlineExption("设备未上线") → 重试（最多 12 次，每次重新 5s 延迟）
整体 amb 65s 定时器 → TimeoutException
```

随后绑定（`WifiBindActivity.bindEquip()` → `EquipPresenter.bindEquip()`）：

```
POST /ai-app/equip/bind   (form-urlencoded)
  id, productId, name, alias, bluetoothMacAddr, wifiMacAddr, sn, model,
  lastStartTime, lastEndTime, type, continued, dialogOks, targetFamilyId(当前家庭)
```

注意：BLE 配网分支里 `bindEquip()` 新建的 `Equip` 只填了 `vender / name / type / sn / productId / alias / model`，**没有 `bluetoothMacAddr`**（扫描时算出的 MAC 在此路径被丢弃）；只有「纯蓝牙绑定」路径会把 `bluetoothMacAddr` 一起上报。

成功链路：

1. `showSuccMask("绑定成功")`
2. `showInitStatusTime > 0` → 进入「初始化」页并倒计时；否则直接回传结果
3. `setResult(RESULT_OK, {"equip": Equip})` + `EventBus.post(EquipBindEvent(true, equip, true))`

进度页状态机（`BaseWifiBindProcessFragment.Status`）：`CONNECTING(0)` → `NETWORK_SETTING(2)` → `BINDING(3)` → `INITIALIZING(100)`；文案对应「连接设备中…」「绑定中…」等。

## 失败处理

`WifiBindActivity.handleError()` 的关键分支（与本链路相关的部分）：

| 异常 | 表现 |
|------|------|
| `BleConnectException("蓝牙连接已断开")`、`EquipNotOnlineExption` | 配网失败弹窗（`showSetupFailDialog(-1)`） |
| `GetSnEmptyException("蓝牙连接已断开")` | 连接失败页 |
| `TimeoutException` / `ConnectException` / `SocketTimeoutException` | 网络错误提示 |
| 倒计时（`showInitStatusTime + 100` 秒）耗尽 | `showSetupFailDialog(-1)` |

> 说明：`configAndBindDefault()` 的 BLE 分支里，连接断开被抛成 `GetSnEmptyException`（消息「蓝牙连接已断开」），走的是「连接失败」页而不是蓝牙重连弹窗。

## 与热点配网的关系

`fromBle=false`（用户在失败弹窗里点「尝试热点配网」，或产品只有 `wifiConfig`）时走同一条 `configAndBindDefault()` 的非 BLE 分支：

1. 若当前 Wi-Fi 不是设备热点，先 `connectSoftApOfEquip()` 连上设备热点（SSID 需匹配 `wifiConfig.ssidPattern`）；
2. 扫地机（`is3irobotics=true`）先 `TcpHelper.tryConnect(ip, port)`，再经 TCP 发 `{"method":"wifi_config","info":{ssid,pwd,addr}}`；非扫地机走 `SetupApHelper.setupAp()`（UDP，SSID/密码以 UTF-8 与 GBK 两种 Base64 同时下发）；
3. 之后同样回到「SN → 上线校验 → 绑定」。

即：**BLE 与热点是同一套「下发凭据 + 取 SN + 云端绑定」流程的两种传输通道**。

## 复刻要点

- 服务/特征 UUID、蓝牙名正则、是否用蓝牙名当 SN，全部来自云端产品配置，不能硬编码；离线复刻需先抓一次 `/ai-app/product/list` 并解密。
- 帧头是 `[seq, len, total]`，下行载荷从第 4 字节开始并在末尾多一个（可忽略的）校验字节；上行第 4 字节是命令字 `0x03`、无校验字节。
- 下行必须限速（约 200 ms/帧）；发完等 2 秒再读，读不满时 100 ms 后重读。
- 读回 SN 后**不要立即绑定**：先轮询 `/ai-app/equip/status` 到 `ON_LINE`（5 s 间隔、上限约 65 s），否则云端会拒绝或绑定到未激活设备。
- `addr` 必须是设备可达的云端域名（去掉 `https://`），否则设备联网后找不到服务。
- 若在 HA 侧复刻：需要具备 **GATT 客户端**能力（连接、按特征写入、按特征读取），并且能完成 Wi-Fi 选择与云端绑定；仅做广播扫描不够。
